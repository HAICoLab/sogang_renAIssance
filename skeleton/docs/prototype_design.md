# Sogang Librarian Copilot — 최소 프로토타입(v0) 설계서

> 도서관 청구기호 부여를 지원하는 사서-AI 협업 에이전트의 **최소 기능 프로토타입(walking skeleton)** 설계 문서.
> 목적: 입력(서지정보) → 출력(852 청구기호 후보 + 판단 근거)이 **끝까지 관통하는 가장 얇은 파이프라인**을 먼저 완성하고, 각 모듈을 순차 고도화한다.

---

## 0. 핵심 결정 요약 (스코프)

실제 사서용 MARC Editor(통합KORMARC) 화면과 「국내서 학생 매뉴얼 ver.3」을 근거로, v0의 목표를 다음과 같이 **좁힌다.**

| 852 하위요소 | v0 처리 방식 | 근거 |
|---|---|---|
| **▼a (관)** | `중앙` 으로 **고정** | 가정 (중앙도서관) |
| **▼b (자료실)** | `단행본` 으로 **고정** | 가정 (단행본서가) |
| **▼h (분류기호)** | ★ **핵심 예측 대상** — AI가 후보+근거 생성 | 정답이 갈리는 "판단" 문제 |
| **▼i (도서기호)** | **해싱 근사 + 중복검사** 로 결정론적 생성 | 매뉴얼: F3 자동생성 → F10 중복검사 |
| **▼m (부가기호)** | **메타데이터 기반 결정론** (번역=K, 개정판=연도) | 매뉴얼: 번역서 무조건 K 등 |

> **결론: v0의 지적 난이도는 ▼h에 집중된다. ▼i·▼m은 규칙/근사로 처리한다.**

### 참고: 082 ≠ 852
- **082** = 교보문고(업체)가 제공하는 DDC. 서지상의 **참고값(prior)**, 원칙적으로 수정하지 않음.
- **852 ▼h** = 학교가 **실제 부여하는 분류기호**. 기본값으로 082 ▼a를 가져오되, 학교 규칙(동양전개·번역서/개정판 동일화·컴퓨터서·법학 등)에 따라 **여기서 조정**한다.
- 따라서 진짜 판단 문제는 **"082를 그대로 쓸까, 학교 규칙으로 바꿀까"** 이며, 이것이 ▼h 결정의 본질이다.
- **주의(데이터 갭):** 보유한 CSV(기존 장서)에는 최종 852만 있고 082가 없다. 그러므로 v0에서 **082는 "있으면 강한 힌트, 없으면 생략"인 선택 입력**으로 취급한다. 평가는 서지정보+검색만으로 852 ▼h를 맞히는 방식으로 수행한다.

### 워크드 예시 (MARC Editor 화면)
```
082 04 ▼a 729 ▼2 23                         ← 업체 제공 DDC (prior)
245 10 ▼a 룸 : ▼b 인테리어 디자이너가 기록한 취향의 공간 72
041 1  ▼a kor ▼h jpn                         ← 일본어 원서의 번역서
110    ▼a 닛켄스페이스디자인
700 1  ▼a 김미화, ▼e 역
852    ▼a 중앙 ▼b 단행본 ▼h [?] ▼i [?] ▼m [?]  ← 우리가 채워야 할 부분
```
- ▼a·▼b = 중앙/단행본 (고정)
- ▼h = 729 유지할지 판단 (예측 대상)
- ▼i = 저자기호 자동생성 대상
- ▼m = 번역서이므로 `K` (결정론)

## 1. 시스템 개요

### 입력 → 출력
```
[입력] 도서 서지정보 (+ 선택: 082 업체 DDC)
   │
   ▼
① 서지 분석      (핵심 주제·형태·번역여부 추출)
② 사례 검색(RAG) (기존 장서에서 유사 도서 top-k)
③ ▼h 분류 결정   (Claude: 후보 + 적합도 + 근거[XAI])   ★핵심
④ ▼i 도서기호    (해싱 근사 + 중복검사)
⑤ ▼m 부가기호    (번역/개정판 규칙)
   │
   ▼
[출력] 완성된 852 문자열 + 후보별 판단 근거
       예)  852 ▼a 중앙 ▼b 단행본 ▼h 729 ▼i 니58ㄹ ▼m K
```

### 설계 원칙
1. **모듈 = 파이프라인 단계.** 각 단계는 "정해진 입력 → 정해진 출력"의 순수 함수. 내부 구현(휴리스틱→LLM, 키워드→임베딩)을 바꿔도 배선은 불변.
2. **v0 외부 의존성 최소화.** Supabase·임베딩·웹UI 없이 **Python + JSON 파일 + Claude API** 만으로 끝까지 실행.
3. **LLM 호출은 ③ ▼h 결정 한 곳에 집중.** 나머지는 순수 파이썬 → 디버깅·검증 용이.
4. **평가 우선.** 홀드아웃 기반 자동 평가 하니스를 초기부터 둔다(성능을 눈으로 확인하며 개선).

## 3. 구성 모듈 상세

> 아래 A~D는 **독립적으로 병렬 개발 가능**하도록 경계를 나눈 것이다. 공통 전제는 §2 스키마와 §5 디렉토리 구조를 **먼저 합의**하는 것.

### 모듈 A. 데이터 · 파싱 · 평가 하니스
**목표:** CSV(기존 장서)를 파이프라인이 쓸 수 있는 정규화 데이터로 만들고, 성능 측정 기반을 마련한다.

- **A-1. CSV → `collection.json` 정규화** (`src/ingest.py`)
  - 입력: `data/books.csv` (검색어·제목·저자·출판사·출판년·청구기호·자료유형·총서명·소장처·대출상태·서지ID·상세URL)
  - 각 행을 BookInput 유사 구조 + `ddc_h`(파싱된 852 분류기호)로 변환.
- **A-2. 청구기호 파서** (`src/parse_callno.py`)
  - `"006.3 이77ㅇ"` → `{ ddc_h: "006.3", book_code: "이77ㅇ" }`
  - 처리할 예외(실데이터에 존재):
    - 로케이션 접두어: `LA 343.0999 …`(법학), `P/PCL 805 …`(정기간행물) → 접두어 분리
    - 청구기호가 `보관서고`뿐인 행 → 소장처 필드에 숨은 `LA 327.12…` 추출 or 제외 처리
    - 소장처/청구기호 복수 표기(`… | …`) → 첫 대표값 채택
    - 판·연도·`K` 등 꼬리표(`005.133 P6이영`, `… 2001/ K`) → ▼m 후보로 분리
  - 산출: 정규화 함수 + 파싱 실패 로그(예외 케이스 목록).
- **A-3. 홀드아웃 평가셋** (`data/holdout.json`)
  - `collection`에서 N권(예: 각 주제 3권 = 15권)을 뽑아 **852 ▼h를 가린** 테스트 입력으로 분리.
  - 나머지는 검색 대상 corpus로 사용.
- **A-4. 평가 하니스** (`src/evaluate.py`)
  - 파이프라인 예측 ▼h vs 실제 ▼h 비교. 지표:
    - **Exact match**: ▼h 완전 일치율
    - **Prefix match**: 상위 분류(주류/강목, 앞 3자리) 일치율
    - **Top-3 hit**: 후보 3개 안에 정답 포함율
    - **참고 baseline**: 검색된 유사도서의 최빈 ▼h(=RAG 다수결)만 썼을 때의 정확도 → Claude가 이를 얼마나 넘는지 확인
  - 산출: 콘솔 리포트 + 오분류 케이스 목록(개선 근거).

### 모듈 B. 서지 분석 · 사례 검색 (RAG)
**목표:** 입력 도서의 주제를 파악하고, 기존 장서에서 유사 도서를 찾아 ③에 컨텍스트로 제공한다.

- **B-1. 서지 분석** (`src/analyze.py`)
  - v0: 휴리스틱. 제목·부제·총서명·키워드를 토큰화하고, 번역여부(041/500 단서)·자료형태를 플래그로 추출.
  - 산출: `Analysis { core_terms[], is_translation, material_type, ... }`
  - (고도화 여지: Claude로 핵심 주제·학문분야 추출로 승격)
- **B-2. 사례 검색** (`src/retrieve.py`)
  - v0: **키워드 겹침 / BM25** 기반 점수화로 corpus에서 top-k(예: k=8) 반환.
  - 각 결과에 `ddc_h`, `similarity`, `match_reason` 포함.
  - 인터페이스: `retrieve(analysis, collection, k) -> [SimilarCase]`
  - (고도화 여지: 임베딩 벡터 유사도로 교체 — 이때 인터페이스 불변)

### 모듈 C. ▼h 분류 결정 (Claude) ★핵심
**목표:** 서지정보 + 082(있으면) + 검색된 유사사례 + 매뉴얼 규칙을 근거로 **▼h 후보와 판단 근거**를 생성한다.

- **C-1. 규칙 컨텍스트 준비** (`data/rules.md`)
  - 매뉴얼에서 ▼h 결정에 관계된 규칙을 발췌·정리:
    - 082 기본 채택 원칙, 동양전개(문학·지리·역사·철학·언어 → 852만 변경, 800대=문학)
    - 번역서: 원서와 동일 분류, 개정판: 초판과 동일 분류
    - 컴퓨터 관련서 별도 전개(예: C언어 005.133)
    - 법학 340번대 로케이션(LA) 등
  - (선택) 사용 DDC 강목 참조표 일부.
- **C-2. 분류 프롬프트 + 구조화 출력** (`src/classify.py`)
  - Claude 호출. **tool use(JSON schema)로 출력 강제** → ClassificationResult(§2.3) 반환.
  - 입력 구성: 도서 서지 + 082 prior + top-k 유사사례(제목·▼h·유사이유) + 규칙 발췌.
  - 행동 지침(프롬프트): **기본은 082/유사사례를 따르되, 규칙이 적용되거나 주제가 명백히 다르면 조정하고, 반드시 근거를 남긴다. 정답이 갈릴 땐 복수 후보와 모호도(ambiguity)를 제시.**
  - **프롬프트 캐싱**: 규칙 발췌 + DDC 참조표 등 고정 컨텍스트는 캐시 블록에 넣어 반복 호출 비용·지연 절감.
  - 모델: 기본 `claude-sonnet-4-6`(가성비), 모호 케이스만 상위 모델로 승급 가능하도록 config 스위치.

### 모듈 D. 도서기호(▼i) · 부가기호(▼m) · 조립 · 실행기
**목표:** 규칙성 요소를 결정론적으로 채우고, 최종 852를 조립해 실행 가능한 CLI로 묶는다.

- **D-1. ▼i 도서기호 생성** (`src/book_code.py`)
  - 매뉴얼 로직 근사(사용자 합의: 해싱 근사 허용):
    1. **성**: 저자명 첫 글자(한글) / 외국인은 성 첫 알파벳 대문자
    2. **숫자**: 성 다음 글자를 2자리 숫자로 변환 — v0는 고정 매핑표(초성·중성 기반) 또는 해시(mod)로 근사
    3. **서명 초성**: 서명 첫 글자의 초성 추가
    - 예) `이77ㅇ` = 이(성) + 77(이름 변환) + ㅇ(서명 초성)
  - **F10 중복검사**: 생성된 `ddc_h + book_code`가 corpus에 이미 있으면 매뉴얼 규칙대로 해소:
    - 같은 저자 → 그 저자 숫자 승계 + 서명 초성 확장
    - 다른 저자 → 중복 숫자 자릿수 확장(예: `48` → `481`, `482`…)
  - **주의:** 실제 리재철 한글순 저자기호표를 완벽 재현하지 않는다. v0는 "재현 가능한 근사 + 중복 무결성" 확보가 목표이며, 정확한 저자기호표 이식은 고도화 과제.
- **D-2. ▼m 부가기호 생성** (`src/suffix.py`)
  - 번역서(041 ▼h 존재 / 041 1 / 500 "…번역서임") → `K`
  - 개정판·2판 → 판 발행연도(예: `2019`)
  - 원서 개정판을 번역 → `2018/K` 형태
  - 해당 없음 → 공란
- **D-3. 조립 + 파이프라인 배선** (`src/pipeline.py`)
  - `classify_call_number(book) -> CallNumber`
  - ① analyze → ② retrieve → ③ classify(▼h) → ④ ▼i → ⑤ ▼m → 852 조립.
- **D-4. 실행기(CLI)** (`src/run.py`)
  - 입력: book_id(홀드아웃) 또는 즉석 서지 JSON.
  - 출력: 완성 852 문자열 + 후보별 근거(사람이 읽을 수 있게).

## 6. 빌드 순서 (마일스톤)

**워킹 스켈레톤 우선 → 모듈 교체 순.**

- **M0 — 스켈레톤 관통 (반나절)**
  - `schema.py` 확정 + 미니 `collection.json`(10건 수기) + `run.py`가 **더미 852를 출력**하도록 배선.
  - 목적: 입력→출력이 끝까지 흐르는지 확인. (Claude 미연결, 스텁)
- **M1 — 데이터 (모듈 A)**
  - CSV 정규화 + 청구기호 파서 + 홀드아웃 분리. `collection.json`/`holdout.json` 완성.
- **M2 — 검색 (모듈 B)**
  - analyze + retrieve(키워드). 홀드아웃 도서로 유사사례가 그럴듯하게 나오는지 확인.
- **M3 — ▼h 분류 (모듈 C) ★**
  - Claude 연결, 구조화 출력, 규칙 컨텍스트 주입. 후보+근거가 나오는지 확인.
- **M4 — ▼i·▼m·조립 (모듈 D)**
  - 도서기호·부가기호 결정론 모듈 + 852 조립. 완성 문자열 출력.
- **M5 — 평가·개선 (모듈 A-4)**
  - 홀드아웃 평가 리포트 → 오분류 분석 → 프롬프트/검색 개선 반복.

> M1~M4 본체 모듈(A·B·C·D)은 M0에서 스키마를 고정한 뒤 **병렬 개발** 가능. 통합은 각 모듈이 스텁을 실제 구현으로 바꾸는 방식으로 진행.

## 7. 평가 방법

- **1차 목표(정량):** 홀드아웃에서 ▼h **Prefix(주류/강목) 일치율**을 우선 지표로 삼는다(완전 일치는 도서기호·판차 영향으로 엄격하므로 2차).
- **2차 목표(정성):** 모호 케이스(같은 키워드·다른 분류)에서 **복수 후보 + 근거의 타당성**을 사람이 검토. 이것이 제안서의 XAI 가치.
- **baseline 대비:** "RAG 다수결 ▼h"만 쓴 값과 Claude 결과를 비교해 **LLM+규칙의 기여**를 수치로 보인다.

## 9. 리스크 · 주의사항

1. **082 부재:** CSV에 082가 없어 "082→852 변환"을 직접 학습·평가할 수 없다. v0는 서지+RAG로 852 ▼h를 추정하고, 082는 선택 입력으로 둔다. (실제 워크플로우 통합 시 082는 강한 prior로 활용)
2. **도서기호 근사:** ▼i는 실제 프로그램의 내부 저자기호 로직과 다를 수 있다. v0는 "재현 가능 + 중복 무결"까지만 목표.
3. **매뉴얼 손글씨:** 여백 필기(암묵지)는 일부만 판독 가능. 규칙 발췌(`rules.md`)는 타이핑된 본문 기준으로 하고, 필기 규칙은 확인된 것만 반영.
4. **데이터 편향:** 현재 corpus는 5개 주제(AI·경제·역사·문학·물리) 100건. 다른 주제 입력은 검색 근거가 빈약할 수 있음 → 평가 해석 시 유의.
5. **API 비용/지연:** ▼h 분류만 LLM 사용. 프롬프트 캐싱으로 규칙·참조 컨텍스트 재사용.
